Observed on-chain. SolvBTC is a beacon proxy: EIP-1967 beacon slot = UpgradeableBeacon 0xFc335FdA7E6a33329A83F4d5F578eC7d8A43DC4A (implementation() = 0xA4b6cf2BAaA235ab7Fe10EADB84b82460165B38F), whose owner() = SolvBTCFactory 0x443628281E4f3E5b5A5D029B9a0D13900ae41578 (getBeacon('Solv BTC') = that beacon). The factory's admin() = TimelockController 0xfd4B809AD88db6Ca9dbB295A4B9d23bB0093f497 (pendingAdmin() = 0) with getMinDelay() = 259200s (3d); governor() = the 3-of-5 Safe 0x0c2Bc4d2698820e12E6eBe863E7b9E2650CD5b7D (pendingGovernor() = 0), which holds the timelock's PROPOSER_ROLE, EXECUTOR_ROLE and CANCELLER_ROLE but not DEFAULT_ADMIN_ROLE (held by the timelock itself; EXECUTOR_ROLE not open). Verified source pinned to runtime code: SolvBTCFactory is a Sourcify exact_match and every beacon-mutating path (setImplementation -> upgradeTo, transferBeaconOwnership, importBeacon) and transferAdmin is onlyAdmin, while onlyGovernor only deploys new beacon proxies; the timelock (SolvTimelock is OpenZeppelin v5.0.0 TimelockController, fully verified on Blockscout, not on Sourcify) reverts schedule when delay < getMinDelay() and only lets itself call updateDelay.

Documented. docs.solv.finance/llms-full.txt: 'The admin privileges for upgrades are assigned to a Gnosis Safe multi-signature address ... The timelock mechanism will be added to further enhance security by introducing a delay between the upgrade proposal and execution.'

  "getMinDelay()" \
  --block 26418060 --rpc-url "$ETH_RPC_URL"
cast block 26418060 --field hash --rpc-url "$ETH_RPC_URL"
